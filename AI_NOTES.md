# AI_NOTES

## Инструменты и ключевые промпты

Работал в VS Code с расширением Codex. Проект и тесты запускал через Docker Compose. Для проверки пользовательских сценариев написал PHP-скрипт с cURL-запросами. Дополнительно использовал Postman и проверял данные в БД. Автоматические проверки выполнялись через PHPUnit и Laravel Pint.

Ключевые промпты приведены дословно.

**1. Подготовка ревью**

```text
Приступай к первой части - составление REVIEW.md

1. Коротко перескажи обязательные требования и границы задания
2. Для каждой найденной проблемы укажи серьёзность critical / major / minor, файл и строку, конкретный сценарий ошибки, минимальный способ исправления.
3. Отметь подозрительные места, которые не являются дефектами.
4. Укажи, что подтверждено чтением кода, что проверено запуском, что остаётся предположением.
5. Дополнительно ещё проверь схему БД в рамках задания на оптимальность и наличие проблем, найденные проблемы, если они найдутся, опиши в тот же список пункта 2

Пиши кратко и предметно, сосредоточься на корректности, безопасности и требованиях задания.
Не редактируй другие файлы.
```

**2. План исправления создания бронирования**

```text
Составь план по исправлению списка проблем из REVIEW.md только для функционала бронирования, отмену брони пока не делаем. Если можно разделить исправление проблемы с конкурентными запросами от основного функционала, то оставить на потом. Если нет, то внести в план сазу. Также необходимо составить тесты и учесть все возможные пограничные случаи для метода бронирования
```

**3. Выбор защиты от конкурентных запросов**

```text
Рассмотри различные варианты по устранению race condition при бронировании: advisory lock, GIST индекс, транзакции. Нужен наиболее простой и минимально удовлетворяющий способ.
```

## Ошибки ИИ и решения после ревью

1. **Расширение рамок задания.** ИИ включил в обязательный план исправление ошибки 500 при отсутствии заголовка `Accept`. На этапе подготовки плана для `store` я исключил эту правку: поведение уже было описано в README и не входило явно в обязательный список изменений.

2. **Избыточно широкий формат дат.** В первоначальном варианте валидация принимала больше вариантов ISO 8601, чем требовалось для выбранного контракта API. При ревью `store` я ограничил формат датой и временем с секундами и обязательным `Z` либо смещением `±HH:MM`. Требование принимать любое смещение сохранилось.

3. **Повторяющиеся тесты.** ИИ генерировал много пограничных случаев, которые фактически проверяли один и тот же путь выполнения. При ревью каждого изменения я сокращал такие тесты, сохраняя проверки различных правил и ошибок.

4. **Проверка диапазона ID при отмене.** ИИ добавил явную проверку формата и диапазона `bigint` для ID брони. При ревью `destroy` я упростил этот участок, оставив числовое ограничение маршрута. Сама проверка диапазона была корректной: её удаление оставляет ограничение — значение выше диапазона PHP `int` может привести к 500.

5. **Изменение HTTP-кода конфликта.** ИИ первоначально предложил заменить 409 на 422 для занятого интервала. При ревью `store` я сохранил исходный контракт: ошибки валидации возвращают 422, конфликт с существующей бронью — 409.

Для устранения гонки после сравнения вариантов выбрал транзакцию с блокировкой строки комнаты: блокировка, проверка пересечения и вставка выполняются в одной транзакции.

## Что проверял самостоятельно

- Читал все изменённые файлы и тесты, сопоставлял поведение с ТЗ и вносил правки вручную. Не принимал сгенерированный код только на основании успешного запуска тестов.
- Написал PHP-скрипт, имитирующий действия пользователя: создание брони, отмену и параллельное бронирование. Скрипт выполнял набор cURL-запросов к API.
- Проверял запросы через Postman и вручную сверял ответы с данными в БД.

Дополнительно конкурентные тесты проверили на временной копии проекта с намеренно ошибочным расположением блокировки вне транзакции. Это выявило ложноположительный результат при синхронизации после INSERT. Синхронизацию перенесли перед вставкой; после исправления оба теста обнаруживают эту регрессию.
